The isolated runner measures fixed-height forward/reverse scrolling, row navigation, native-container reach, mount-to-visible latency, wheel movement, width resize, basic Page Down behavior where focusable, mounted rows, JS heap/backing storage, long tasks and externally bounded failure outcomes. It runs all seven at 100K, 1M and 100M, three passes each. These are adapter-level measurements, not complete accessibility or variable-height coverage. Separate table pages also benchmark native document scrolling for VitScroll, TanStack Virtual, React Virtuoso and react-virtualized; see the README for integration limits and browser tests.

## What belongs to which layer?

Search finds matching records; filtering produces a subset; sorting changes their order. A virtualizer decides which of those records to render. For most libraries here, the application supplies the processed data. Giving one library a faster search algorithm would not establish that its virtualizer is faster.

AG Grid is a full grid and has data features. However, our adapter uses its **Infinite Row Model**, which delegates filtering and sorting to the datasource. Its built-in Quick Filter requires the **Client-Side Row Model**. A test of that feature needs a separate AG Grid adapter and separately labeled results.

Browser Find is a different feature from application search: unmounted rows generally cannot be found by searching current DOM text. An application search benchmark must query the dataset, not just rendered elements.

Search/filter/sort plus stable identity is the best next runnable slice. It resembles real list use, applies to all seven through a shared application data layer, and exposes failures that smooth fixed-height scrolling cannot.

## Fair measurement protocol

1. Generate one seeded dataset with stable IDs outside the timed region. Begin with 10K and 100K; only add 1M after bounded memory and runtime checks. Keep the 100M coordinate experiment separate.
2. Use one deterministic predicate, normalization rule, sort comparator and tie-breaker for every adapter. Define the query before measuring. Separate exact-ID lookup from case-insensitive text search; do not silently give only one adapter an index.
3. Report three boundaries: **processing** (query start to ordered IDs ready), **render settle** (apply IDs to correct visible DOM), and **end-to-end** (user action to correct visible result). The sum of the first two is not necessarily end-to-end when scheduling/debounce overlaps; record actual timestamps. Report debounce separately.
4. Keep an adapter mounted while applying mutations; remounting it would test mount cost instead of update behavior. Extend the common contract with stable item IDs, result revision, ordered row access and an explicit update method. The existing `key` containing count and row height is only suitable for the current fresh-mount scrolling benchmark.
5. Render `data-row-id`, visible index and result revision. Wait until the expected IDs and geometry are correct for two consecutive animation frames. Stop after a declared 2-second timeout. A timeout is a failure, not a fast sample. Two-frame confirmation gives an operational settle measurement, not exact physical display latency.
6. For filtering, start with a common "reset to first result" policy. Test anchor preservation separately when supported. For prepend, compare the same anchor ID before and after, not the old index. Use stable keys through all adapters; the current VitScroll prototype will need an explicit key/data contract.
7. Warm each scenario up, then run 20 operations per pass across 3 rotated passes. Retain raw samples and show p50/p95 plus failure count, dataset size, version, viewport, browser, build and buffering policy. Keep cold and warm-cache tests separate.
8. Instrument blank/overlapping rows, stale revisions and focus loss. Optional PerformanceObserver long-task data must be feature-detected and reported as unavailable where unsupported. Do not estimate heap memory from mounted rows or bundle size.
9. Separate capability status (**documented**, **integration required**, **unsupported in this configuration**, **unverified**) from execution status (**passed**, **failed**, **not run**). Never put zero milliseconds in an unsupported cell or combine correctness and speed into one score.
10. For native AG Grid search/filter, create a separate Client-Side Row Model cohort using the same full dataset and declared matching semantics. Report it as a complete grid/data-pipeline comparison, not the same renderer-only leaderboard. Preserve the existing Infinite Row Model results.
